- **The template drift gate no longer calls a merged branch "an archived version edited after it shipped."** Leg (vii) of `tools/template_drift_gate.py` counted every commit `origin/main` could reach that touched an archived directory, so a branch that added an archive and corrected it in review (the sequence `docs/BUILDING.md` requires: a green gate before review, fixes in their own commit) was fine until `tools/land.py` merged it, and then failed CI on `main` itself: `notes/_versions/1.3`, added and amended on one branch, landed 20261102 as one merge commit with three commits behind it, and the `template-drift` job went red (the other 15 jobs of that run passed). Earlier archives (`1.1`, `1.2`) each had exactly one commit, so the leg had never been asked. It now counts steps along `origin/main`'s first-parent chain, which is what its own docstring called "landed, never committed": a merged branch is one entry however many commits it carried, a *second* landing that touches the directory is a second entry and is still refused, an edit in the working tree against the published ref is still refused, and a branch fast-forwarded onto `main` (which `land.py` never does) counts every commit it brings. Three tests pin the three cases, and the first of them was red on the unfixed gate. **One limit, found by a fresh reviewer's 31 history shapes and recorded as limit (e) in the gate's header:** a `git pull`-style merge (the local commit as first parent) pushed over a `main` that was already red puts the shipped commits behind one merge commit and turns it green with no fix; `tools/land.py` never makes that merge, the gate run before such a push still reports `differs from origin/main`, and no rule over the graph alone can tell it from a `land.py` landing. Nothing in a wheel changes.
